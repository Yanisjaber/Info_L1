Ce cours a deux parties qui n'en font qu'une : on écrit proprement pour pouvoir changer son code, et on le teste pour pouvoir le changer sans le casser. La décomposition en fonctions est le pont entre les deux : elle produit les fonctions que les tests savent examiner.

Partie I — Habitudes d'écriture

1. Pourquoi le clean code

Objectifs : sensibiliser à quelques dispositifs qui améliorent la qualité d'un code (Clean code) pour qu'il réponde mieux aux attentes de ceux à qui il s'adresse (relecteurs, collaborateurs, clients…), et à la nécessité professionnelle de « bien écrire ».

Clean code — L'objectif principal du Clean code est la construction de logiciels en minimisant le coût du changement (évolution du besoin, changement de l'équipe qui gère…) et en maximisant la capacité à répondre au changement.

La définition est économique, pas esthétique : un logiciel est modifié bien plus souvent qu'il n'est écrit, et chaque modification coûte d'autant plus cher que le code est difficile à comprendre.

Les quatre pistes de travail

Deux autres pistes

  • KISS (Keep It Simple, Stupid) : éviter l'optimisation prématurée. On écrit d'abord un code simple et correct ; on n'optimise que si une mesure montre que c'est nécessaire.
  • Règle du boy scout : laisser le code source plus propre que quand on l'a trouvé. Une petite amélioration à chaque passage, plutôt qu'un grand nettoyage qui n'arrive jamais.

2. Nommer

Le cours part d'une carte de France du « pain au chocolat / chocolatine » et d'une citation d'Ambroise de Milan : Si fueris Romae, Romano vivito more — « À Rome, fais comme les Romains ! ».

Principe général — les conventions changent selon le langage, l'entreprise, les personnes avec qui on travaille ; la compétence visée est donc de s'adapter et de les utiliser selon le contexte. Il n'y a pas de « bonne » convention dans l'absolu : voici celles de l'UE Info1.Algo1.

Les conventions de l'UE

  • en français, pour la bonne compréhension ;
  • des noms précis ;
  • un nom de variable reflète ce que représente la variable ;
  • un nom de fonction reflète ce que fait la fonction — le quoi, pas le comment — si possible avec un verbe d'action ;
  • refléter le niveau d'abstraction : un nom fonctionnel au niveau fonctionnel, un nom technique au niveau technique.

3. Commenter

Commenter pour expliquer

  • en cours de développement : indiquer l'intention pour les lignes suivantes (quitte à supprimer ensuite) ;
  • certains commentaires — tous ? — peuvent être évités quand le nommage est bien fait ;
  • indiquer le pourquoi, et pas le comment.

À faire — on explique le pourquoi :

# Division entière pour éviter les flottants
moyenne = somme//nb_elements

À éviter — on paraphrase le code :

# Division de la somme par le nombre d'éléments
moyenne = somme//nb_elements

Le second commentaire ne fait que redire la ligne en français : il ajoute du texte à maintenir sans ajouter d'information. Le premier explique un choix que le code seul ne révèle pas — pourquoi // plutôt que /.

Commenter pour structurer

Sur un code long (au-delà de 1000 lignes par exemple), les commentaires servent à identifier la structure : titres et séparations entre les parties fonctionnelles ; ne pas dépasser 80 caractères par ligne.

# FONCTIONS ENTREES-SORTIES
def ...

# FONCTIONS UTILITAIRES
def ...

# TRAITEMENT PRINCIPAL
def ...

# PROGRAMME PRINCIPAL
...

Cette structure n'est pas décorative : elle annonce exactement la décomposition de la section suivante.

4. Décomposer

Avantages de la décomposition en fonctions — lisibilité ; modularité et réutilisabilité (dans le même programme ou dans d'autres) ; testabilité et maintenance (tests unitaires, diagnostic d'erreurs, mises à jour).

Le troisième point fait le lien avec la partie II : on ne peut tester unitairement que ce qui a été isolé dans une fonction. Décomposer n'est pas une coquetterie de style, c'est la condition d'existence des tests.

La méthode : de haut en bas

On commence par le programme principal :

# PROGRAMME PRINCIPAL
entrees = saisie_des_donnees()
sorties = fonction_de_traitement(entrees)
affichage_des_donnees(sorties)

Puis on remonte en précisant les étapes du traitement :

def fonction_de_traitement(entrees):
    fonction_utilitaire_1(...)
    fonction_utilitaire_2(...)
    return ...

(entrées / sorties)		fonction_de_traitement
appelle utilitaire_1 et utilitaire_2 (étapes du traitement, testables unitairement)		affichage_des_donnees

On écrit d'abord le niveau le plus abstrait — le quoi — puis on descend vers le comment. Les fonctions du bas ne font ni saisie ni affichage : ce sont exactement celles que la partie II saura tester.

L'exemple du cours

Le code suivant permet à l'utilisateur de saisir une liste d'entiers dont on calcule la moyenne, puis constitue et affiche la liste des nombres supérieurs ou égaux à cette moyenne. Il s'agit de le décomposer en fonctions pour améliorer la lisibilité.

Avant — 16 lignes, tout au même niveau :

nb_elements = int(input("Nombre d'elements a saisir : "))
liste = []
for _ in range(nb_elements):
    valeur = int(input("Saisir un entier : "))
    liste.append(valeur)
somme = 0
for valeur in liste:
    somme += valeur
moyenne = somme/nb_elements
liste_superieurs = []
for valeur in liste:
    if valeur>=moyenne:
        liste_superieurs.append(valeur)
for valeur in liste_superieurs:
    print(valeur,end=' ')
print()

Après — proposition de correction, suivant la structure en quatre sections. Le programme principal se lit en trois lignes.

# FONCTIONS ENTREES-SORTIES
def saisie_des_valeurs():
    nb_elements = int(input("Nombre d'elements a saisir : "))
    valeurs = []
    for _ in range(nb_elements):
        valeurs.append(int(input("Saisir un entier : ")))
    return valeurs

def affichage_des_valeurs(valeurs):
    for valeur in valeurs:
        print(valeur, end=' ')
    print()

# FONCTIONS UTILITAIRES
def moyenne(valeurs):
    somme = 0
    for valeur in valeurs:
        somme += valeur
    return somme / len(valeurs)

# TRAITEMENT PRINCIPAL
def valeurs_superieures_a_la_moyenne(valeurs):
    moyenne_des_valeurs = moyenne(valeurs)
    superieures = []
    for valeur in valeurs:
        if valeur >= moyenne_des_valeurs:
            superieures.append(valeur)
    return superieures

# PROGRAMME PRINCIPAL
valeurs = saisie_des_valeurs()
superieures = valeurs_superieures_a_la_moyenne(valeurs)
affichage_des_valeurs(superieures)

Ce qu'on a gagné : moyenne et valeurs_superieures_a_la_moyenne ne contiennent ni saisie ni affichage. Elles prennent des paramètres et renvoient un résultat : ce sont des fonctions testables. Au passage, moyenne est réutilisable ailleurs.

5. Factoriser

Factoriser — repérer des fonctions dont le code est très ressemblant ; mettre en commun les parties de code identiques ; les différences amènent à rajouter un ou plusieurs paramètres supplémentaires.
Attention — copier-coller du code produit du code presque identique, donc factorisable. Le copier-coller n'est pas interdit : c'est un signal qu'il y aura quelque chose à factoriser juste après.

L'exemple du cours

Un point mobile est repéré par ses coordonnées (x, y). Il s'agit de factoriser les trois fonctions monter, descendre et droite.

Avant — trois fois la même mécanique :

def monter(point):
    x, y = point
    return (x, y+1)

def descendre(point):
    x, y = point
    return (x, y-1)

def droite(point):
    x, y = point
    return (x+1, y)

Après — la partie identique est « décomposer le point, puis renvoyer un point translaté ». Les différences sont les deux valeurs ajoutées à x et y : elles deviennent deux paramètres.

def deplacer(point, dx, dy):
    # dx et dy : déplacement demandé sur chaque axe
    x, y = point
    return (x + dx, y + dy)

def monter(point):
    return deplacer(point, 0, 1)

def descendre(point):
    return deplacer(point, 0, -1)

def droite(point):
    return deplacer(point, 1, 0)

def gauche(point):
    return deplacer(point, -1, 0)

Les trois fonctions d'origine peuvent disparaître au profit d'appels directs (deplacer(point, 0, 1), deplacer(point, 0, -1), deplacer(point, 1, 0)) ou être conservées comme noms de commodité, ce qui garde un vocabulaire lisible au niveau d'abstraction supérieur. Le bénéfice se voit à la dernière ligne : ajouter gauche coûte une ligne au lieu de trois, et une correction de bug dans le déplacement se fait à un seul endroit — « minimiser le coût du changement ».

Partie II — Tests unitaires

6. Le cadre et l'objectif

Cadre du problème — le cadre d'étude est celui des fonctions. Il se généralise à tout code présentant une ou plusieurs entrées et une ou plusieurs sorties : programme principal, portion de code.

On exclut deux situations :

  • les interactions avec l'utilisateur : dans le cadre étudié, les entrées sont données simultanément et les sorties recueillies simultanément ;
  • les effets de bord non testables : affichage, etc.
Objectif — étant donnée une fonction, répondre à la question : la fonction effectue-t-elle bien ce qu'on attend qu'elle fasse ?

Ces exclusions expliquent la section 4 : une fonction qui fait un input ou un print au milieu de son traitement est hors cadre. C'est pourquoi la décomposition sépare les entrées-sorties du traitement.

7. Les jeux de tests

Jeu de test — un jeu de test permet de spécifier, pour une fonction et des paramètres donnés, la valeur de retour attendue.
Méthode — pour vérifier qu'une fonction répond au problème posé : la tester sur des jeux de tests couvrant le maximum de cas possibles ; trouver les cas particuliers, les cas extrêmes, les cas généraux. Objectif : mettre en défaut le code à tester.

On n'écrit pas des tests pour se rassurer, mais pour essayer de casser sa propre fonction. Un test qui passe du premier coup sur le cas le plus banal n'apprend presque rien ; c'est la liste vide, le singleton ou la valeur limite qui révèle les bugs. On étudie ainsi la couverture de tests, les domaines des paramètres et des valeurs de retour — étude qui se poursuivra avec la spécification de fonction.

La méthodologie d'élaboration des tests sera vue plus en détail dans l'UE Info2.ILU1. En Info1.Algo1, on peut vous demander d'élaborer des jeux de test de deux façons :

  • boîte noire : sans connaître le code de la fonction ; les cas à traiter sont donnés explicitement ;
  • boîte blanche : le code de la fonction est donné ; les cas sont caractérisés par la façon dont la fonction les exécute.

Fonction d'exemple : une liste est un palindrome si elle se lit de la même manière dans les deux sens. est_palindrome accepte une liste d'entiers et retourne le booléen indiquant si la liste est (True) ou non (False) un palindrome.

8. Test en boîte noire

Boîte noire — on ne connaît pas le code de la fonction : on se base uniquement sur l'énoncé pour écrire les tests ; on peut donc les écrire avant la fonction ; on cherche à couvrir l'intégralité des besoins identifiés dans l'énoncé.

9. Test en boîte blanche

Boîte blanche — on connaît le code de la fonction : on s'appuie dessus pour identifier les cas à tester ; on écrit donc les tests après la fonction. Un jeu de tests qui couvre l'intégralité des lignes d'une fonction est dit complet.

Implémentation fournie par le cours :

def est_palindrome(liste):
    i,j = 0,len(liste)-1
    while i<j:
        if liste[i]!=liste[j]:
            return False
        i += 1
        j -= 1
    return True

Deux indices se déplacent l'un vers l'autre depuis les extrémités. Les cas à tester ne se décrivent plus par la forme de la liste, mais par ce que fait la boucle.

Noire vs blanche — plusieurs jeux se ressemblent, mais la justification change. En boîte noire, [1, 2, 2, 1] est « une liste paire qui est un palindrome » ; en boîte blanche, c'est « le cas qui fait deux tours complets ». C'est cette justification qui est demandée en examen.

10. Mise en œuvre : l'instruction assert

Principes pour les tests — éviter les interactions utilisateur (saisie, affichage) exigeant une vérification humaine entre l'obtenu et l'attendu ; automatiser les tests ; les regrouper dans une fonction que l'on peut décider d'appeler ou non.
Assertion — expression booléenne qui doit être évaluée à vrai. Si elle est évaluée à faux, l'exécution du programme s'arrête. (Fonctionnalité présente dans quasiment tous les langages.)
assert <expression booleenne>, "message d'erreur"

Sémantique : le message d'erreur est affiché si l'assertion est évaluée à faux ; sinon l'exécution est silencieuse. Schéma : on compare obtenu et attendu ; s'ils sont égaux, exécution silencieuse et le programme continue ; sinon le programme s'arrête et affiche le message. Un test qui réussit ne dit rien : c'est ce qui permet d'en enchaîner des dizaines. Le silence est la bonne nouvelle.

Fonction de test — on regroupe tous les jeux de tests associés à une fonction dans une fonction de test nommée test_<nom fonction a tester>(...).

Question 4 du cours : la fonction de test

def test_est_palindrome():
    # Cas extrêmes
    assert est_palindrome([]) == True, "palindrome : liste vide"
    assert est_palindrome([7]) == True, "palindrome : singleton"
    # Longueur impaire
    assert est_palindrome([1, 2, 1]) == True, "palindrome : impaire oui"
    assert est_palindrome([1, 2, 3]) == False, "palindrome : impaire non"
    # Longueur paire
    assert est_palindrome([1, 2, 2, 1]) == True, "palindrome : paire oui"
    assert est_palindrome([1, 2, 3, 4]) == False, "palindrome : paire non"
    # Cas issus du code (boîte blanche)
    assert est_palindrome([1, 2]) == False, "palindrome : sortie au 1er tour"
    assert est_palindrome([1, 2, 3, 1]) == False, "palindrome : sortie au 2e tour"
    print("test_est_palindrome : tous les tests sont passes")

On appelle ensuite test_est_palindrome() depuis le programme principal — et on peut décider de ne plus l'appeler une fois la mise au point terminée.

11. Compléments et pièges

Assertions et efficacité

Les assert peuvent être coûteuses en temps ou en mémoire. Après la mise au point, on peut désactiver toutes les assertions en lançant Python en mode optimisé (-O ou -OO) :

python3 -O fichier.py
Attention — assert est exclusivement réservée au débogage. Les assertions étant désactivées en mode optimisé, elles ne doivent pas intervenir dans le fonctionnement d'un programme autrement que pour en vérifier la correction. En particulier : les expressions des assertions ne doivent pas avoir d'effets de bord (exemple à éviter : assert liste.append(5)==None — en mode optimisé, l'ajout ne se ferait plus) ; elles ne doivent servir ni à valider des entrées utilisateur, ni le contenu de fichiers.
Ne pas confondre — l'instruction assert vérifie une assertion exécutable. Elle est distincte des assertions formelles qui guident un outil de preuve d'algorithme — vues en Info2.Algo2.
Pour aller plus loin — une librairie dédiée (unittest…) permet de structurer les tests en modules, classes et fonctions, d'avoir un jeu d'assertions plus riche, de lancer automatiquement les tests et d'obtenir un retour d'exécution par test. Vue en Info2.ILU1 ; lecture conseillée : realpython.com/python-assert-statement.
